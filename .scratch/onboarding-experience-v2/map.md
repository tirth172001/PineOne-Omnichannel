wayfinder:map

## Destination

A working, prototyped v2 revision of the onboarding + login/signup experience for Pine One Omnichannel that closes the following UX gaps against the currently-shipped flow: Singpass consent transparency (what data gets fetched, before it's fetched), a redesigned right-side preview panel (organized/accordion-style instead of merged, and present through KYC too), one CTA per decision instead of two, neutral avatar treatment instead of colored per-index backgrounds, a restructured review-and-sign screen (agreement left, business details right, single sign CTA), a consolidated login/signup flow (email → password → OTP as one seamless sequence), back navigation across the whole journey, and consistent fade-based motion on both sides of the layout at every sub-step transition. Each ticket lands as real, working code in this repo as it resolves — same convention as the v1 map, not a spec-only pass.

## Notes

- Domain: Pine One Omnichannel (Pine Labs) merchant onboarding, **Singapore market** (Singpass/Corppass digital ID, ACRA corporate registry, NRIC/FIN identity documents, UEN business registration). Same domain as the v1 map — see `docs/flows/onboarding-and-auth.md` for baseline flow behavior.
- **Prior map:** [`.scratch/onboarding-experience/map.md`](../onboarding-experience/map.md) — closed, all 18 tickets resolved. Its "Decisions so far" describe the *current, shipped* behavior this map is revising. Do not re-litigate anything it decided except where a ticket below explicitly targets it.
  - **Explicit reversal:** v1's Notes ruled login/signup redesign out of scope ("login is treated as functionally fine"). This map reverses that — see ticket 07.
  - **Correction to a v1-era assumption:** "accordion" for the preview panel was never the shipped pattern anywhere in this codebase — it appeared once as a *rejected* variant for website/app-details (v1 ticket 05) and was never adopted. Treat "accordion-style organization" in ticket 02 as a new design direction to invent, not a pattern to resurrect from existing code.
- Existing components: `components/onboarding/` (`account-onboarding-flow.tsx`, `onboarding-rail-shell.tsx`, `onboarding-preview.tsx`, `onboarding-person.ts`, `onboarding-person-card.tsx`, `onboarding-sequence.ts`, `step-progress-bar.tsx`); auth in `app/login/page.tsx` (no `app/signup/page.tsx` exists — signup is a step inside the onboarding flow, not a separate route). No back-navigation exists anywhere in the current shell or login page today (verified by reading the code) — ticket 08 is additive, not a fix to broken behavior.
- Reference assets (from the user, for ticket 01): a "Login to Singpass" modal (Corppass ID/password + QR "Instant login" option) and a "Singpass consent" modal listing exactly what will be fetched — Additional details (UEN Registration Number, Business Name, Merchant type, Nature of business, Date of Incorporation, Registered Address, Business Owner Details) and Personal details (NRIC/FIN, Name, Email ID, Contact details) — with Proceed/Cancel and a terms-of-usage line. Once "Proceed" is clicked, the flow moves straight to the next step with fetched fields already populating the right-side preview (no separate re-confirmation screen). Singpass wordmark saved at `public/brand/singpass-logo.svg`.
- Skills: `/prototype` for the visual/behavioral tickets (most of this map — "how should it look/behave" questions). `/flow-architecture` for ticket 07 (login/signup sequencing). `/motion-design` skill for ticket 09. `/domain-modeling` only if new vocabulary surfaces.
- This is a Next.js/Tailwind demo repo with an established design system (`app/component-docs/`) and its own decision-log convention (`docs/decisions/decision-log.md`) — new UX decisions from this map should also be reflected there once implemented, per the repo's working rules.

## Decisions so far

- [Singpass login + consent modal](issues/01-singpass-consent-and-login-modal.md) — two-stage `Dialog` (Corppass login form + QR panel, then a two-column consent checklist matching the user's reference screenshots) replaces the direct `startVerification("singpass")` call; Proceed hands off straight to business-basics with the preview populated, skipping the old fields-list confirm screen entirely for the Singpass path (manual-upload path unchanged). V1's first-attempt-fails pattern is preserved; "Try again" now reopens the dialog. Found and fixed a real bug along the way: the Singpass wordmark's black ink was invisible on this app's dark dialog surface, fixed with a white backing chip.
- [Remove colored avatar backgrounds](issues/05-remove-avatar-background-colors.md) — `PersonCard` now uses the repo's existing neutral `AvatarFallback` convention (`bg-muted text-muted-foreground`, already used on the account page) instead of the deleted `colorForIndex`/`personColors`; the now-pointless `index` prop was removed from `PersonCard` and all three call sites. Applies everywhere `PersonCard` renders — business-owners, authorised-signatory, and the persistent preview panel.
- [Consolidate login/signup](issues/07-consolidate-login-signup-flow.md) — the ticket's premise (existing email/password/OTP steps to smooth) turned out to be false; nothing like that existed anywhere in the codebase, so this became "build the account-creation sequence from scratch." Built at `/signup/*` as 5 distinct routed steps (email → password → OTP → business-name → a new "how would you like to get started" fork) sharing a new persistent shell that mirrors `app/login/page.tsx`'s exact panel split via a newly-extracted `AuthVisualPanel`; the fork lands on the two destinations the v1 map's original destination described but never built (`/onboarding/business-verification` and `/onboarding/request-access-existing-merchant`, both pre-existing and untouched). Fixed `app/login/page.tsx`'s "Sign up" link, which previously 404'd. This resolution defines the step boundaries ticket 08 (back navigation) now unblocks against.
- [Add back navigation](issues/08-add-back-navigation.md) — one reusable `router.back()`-driven `<BackButton />`, wired into just two shared components (`StepProgressBar` for the whole onboarding sequence, `SignupShell` for signup) rather than any of the 14 individual step files — the mapping between "screen shows a progress bar" and "screen should offer back" turned out to be exact, so no per-screen back-hiding logic was needed. `request-access-existing-merchant` deliberately excluded (separate chat-style surface). No field-value restoration on back — matches the rest of the app's existing conventions.
- [Establish the redesigned preview-panel direction](issues/02-establish-preview-panel-redesign.md) — document mode is now a real accordion (this repo's existing `components/ui/accordion.tsx`, previously unused in onboarding): completed sections collapse to a summary row, the active section auto-expands and is highlighted, upcoming sections stay locked and label-only. Signatory mode now leads with the signatory's `PersonCard`, with the Letter of Authorisation demoted to a collapsed accordion row — the component ticket 03 will reuse. Graduated the "remaining modes" fog into [banking](issues/10-apply-preview-redesign-to-banking-mode.md) and [owners](issues/11-apply-preview-redesign-to-owners-mode.md) tickets.
- [Apply preview redesign to banking mode](issues/10-apply-preview-redesign-to-banking-mode.md) — resolved as a lighter consistency pass, not a structural accordion (banking has no sub-steps to collapse against each other). Borrowed just the icon-circle-plus-label header grammar from document mode, with the same active-highlight treatment while reading and the same checkmark-circle treatment once confirmed.
- [Establish the sub-step motion pattern](issues/09-establish-substep-motion-pattern.md) — new `<StaggerFields>`/`<StaggerField>` primitives (`components/onboarding/stagger-fields.tsx`) give field-level fade-out-up/fade-in-from-below choreography, replacing the whole-panel `subStepFade` in both shells (now neutralized so nested field motion does the work — exit propagation still lets old fields animate out). New `<RevealField>` (`reveal-field.tsx`) crossfades the preview panel's skeleton→value swaps instead of an instant DOM swap — applied everywhere in `DocumentBody`. Proven on `business-basics` and `/signup/password`; rolling onto the rest graduated into [ticket 12](issues/12-apply-motion-pattern-to-remaining-screens.md), which also resolves the "does this need exceptions" fog question below.
- [Add KYC-stage signatory preview](issues/03-kyc-stage-signatory-preview.md) — face-authentication moves out of `FULL_WIDTH_ROUTES` into the standard split layout, sharing ticket 02's `"signatory"` preview mode with `authorised-signatory` (whole KYC macro, one mode) — `SignatoryBody`/`PersonCard` reused as-is, and the verifying→verified badge animation came for free since `_variant-a.tsx` was already calling `setVerificationStatus` during capture. `_variant-a.tsx`'s wrapper/width also aligned to the shared `max-w-[420px]` split-panel convention.
- [Single-CTA signatory selection](issues/04-single-cta-signatory-selection.md) — removed the `signed` intermediate state; selecting a `PersonCard` (or adding one via the sheet) directly arms a single "Continue" CTA, no "Confirm signatory" interstitial. `PersonCard`'s existing selected-state ring/highlight plus the persistent preview panel already give enough visual acknowledgment of the pick — no new UI needed.
- [Restructure review-and-sign](issues/06-restructure-review-and-sign.md) — genuine two-card split (agreement left with a bounded scrollable region + checkbox + single "Sign agreement" CTA in the same card; read-only business-details summary right, not ticket 02's live/accordion pattern since this route's data isn't threaded through shared state and nothing's left to fill in). Found and worked around a real gap: `OnboardingRailShell` doesn't propagate `h-full` for full-width routes, so this card pair sizes to content with a scroll fallback rather than independently filling the viewport.
- [Apply preview redesign to owners mode](issues/11-apply-preview-redesign-to-owners-mode.md) — lighter consistency pass, no accordion (owners is a growing list, not sections): header row borrows the icon-circle-plus-label grammar, with `active` (primary highlight ring) and `complete` (success checkmark, 100% allocated) states only — an "over-allocated" state was ruled out since the add-owner sheet already blocks totals over 100%.
- [Apply motion pattern to remaining screens](issues/12-apply-motion-pattern-to-remaining-screens.md) — mechanically rolled `<StaggerFields>`/`<StaggerField>` onto all 12 remaining step files (multi-branch screens wrapped each conditional branch's blocks independently). Exception question resolved as predicted: no motion treatment for face-authentication's capture phase or review-and-sign's success screen — no "fields" to choreograph. Fixed a real `w-full` regression on banking-details' upload button exposed by the new wrapper; flagged a pre-existing, unrelated Radix accordion SSR hydration mismatch as a separate task rather than fixing it here.

This map's frontier is now clear — all 12 tickets resolved, nothing left to decide before this v2 revision is fully specified and implemented.
