## Question

Today every step's `_variant-*.tsx` renders its own bespoke right-side preview built only from that step's local state (e.g. `business-verification` shows a document, `business-owners` shows a conic-gradient donut, `authorised-signatory` shows a Letter of Authorisation) — each swap feels like a different preview, and nothing filled in on an earlier step stays visible on a later one. The user wants the preview to feel **seamless and cumulative**: whatever's been filled in throughout the journey stays visible in the same preview object as it evolves.

Architect a single preview component mounted once for the whole post-business-name sequence, fed by accumulated form state across all steps (business profile fields from tickets 02–05, banking from ticket 06, the unified Person list from [Unify Owner/Signatory into one Person model + card](14-unify-person-model-and-card.md), the signed agreement from ticket 10). Decide how it transitions between "modes" as the user progresses (document → banking receipt → person-card list → signed letter) so it reads as one continuously-evolving artifact rather than a swapped component — and how that coexists with the shimmer/expand-to-center-stage "verifying" moment already decided in ticket 01's Notes, and with the reinstated left rail and continuous progress bar from [Revise progress shell and sub-step transitions](12-revise-progress-shell-and-transitions.md) (which determines the layout width this preview has to work within).

Specifically for the business-owners section of the preview: replace or supplement the current conic-gradient donut (which the user reports doesn't read well) with the person cards from ticket 14 — each owner's card appearing as they're added, gaining a "Signatory" badge when chosen in the authorised-signatory step, and a verified badge once that person completes face authentication.

## Answer

**Architecture: hoisted the preview into the shell, not into each route.** A component that lives inside a per-route file necessarily remounts on every navigation (even client-side SPA nav swaps the mounted tree at the route boundary) — so true persistence required moving the preview out of the 7 `_variant-*.tsx` files and into `onboarding-rail-shell.tsx` itself, as a **sibling** of the `AnimatePresence`-animated `{children}` slot, not nested inside it. This is the load-bearing decision: only the left input panel now fades between sub-steps; the preview panel is never unmounted while the user stays within the 7 split-screen routes (business-verification → … → authorised-signatory), so it never "swaps" — it's the same component instance the whole time, exactly what the user asked for.

**New shared modules:**
- `components/onboarding/onboarding-profile.ts` — accumulated form state (verification, basics, store, webApp, banking, a generic `verifying` flag) as a module-scoped store, same `useSyncExternalStore` pattern as ticket 14's `onboarding-person.ts`. Each of the 7 step files keeps its own local `useState` (no risky rewrite of working logic) and syncs into this store via a `useEffect`.
- `components/onboarding/onboarding-preview.tsx` — the single persistent `OnboardingPreview`. One constant outer frame (Grainient background, card border, "Business Profile" header) — only the body content crossfades between 4 modes as `getPreviewMode(slug)` changes: **document** (business-verification/basics/store/website-app-details — merges what were 4 separate preview components into one, revealing fields progressively based on how far the user has gone), **banking** (banking-details), **owners** (business-owners — replaces the conic-gradient donut the user flagged as unreadable with a live `PersonCard` list, exactly as asked), **signatory** (authorised-signatory — the existing Letter of Authorisation, now reading the real shared signatory). The header's badge shows a running **"N details confirmed"** count computed across the *entire* accumulated profile + person list — it only ever grows, reinforcing cumulative progress across the whole journey, not just the current step.
- `onboarding-sequence.ts` gained `FULL_WIDTH_ROUTES` (face-authentication, review-and-sign — ticket 01's exceptions, unchanged: no preview panel at all) and `getPreviewMode(slug)`.

**Verifying/shimmer moment:** preserved via the same `verifying` boolean (set by business-verification during Singpass/upload connection, and by banking-details during statement reading) driving the same shimmer-sweep overlay on the persistent card — now one shared implementation instead of two near-duplicate ones.

**Found and fixed a real bug while building this:** store-verification's uploaded photo used a blob object URL that was revoked (`URL.revokeObjectURL`) on component unmount. Since the preview needs that URL to keep working *after* the step's own component unmounts (that's the whole point of persistence), the revoke-on-unmount cleanup would have broken the photo the moment the user left the store-verification step. Removed it — the URL now only gets revoked when replaced by a new upload.

**Verified end-to-end in-browser:** clicked through business-verification (Singpass) → business-basics → store-verification → website-app-details, confirming the document card never reset and the "N details confirmed" count climbed 4→5→6→8 live as fields were filled; crossed into banking-details and confirmed the mode crossfaded while the header/count persisted; crossed into business-owners and confirmed the preview showed a live, real `PersonCard` (not the donut) matching the input list exactly; crossed into authorised-signatory and confirmed the mode switched to the letter and filled in live on selection; confirmed face-authentication and review-and-sign both correctly render with no preview panel at all (full-width). No console errors at any point; `tsc --noEmit` clean on every file touched.

**Known limitation, called out explicitly (not something this ticket was asked to solve):** the shared stores are module-scoped, so they survive Next.js client-side navigation between these routes but reset on a hard reload or a non-SPA navigation (e.g. typing a URL directly) — same caveat ticket 14 already established for the Person store. A real backend or a persistence layer (localStorage, server session) would be the next step if this needs to survive reloads, but that's beyond what "architect the preview panel" asked for.
