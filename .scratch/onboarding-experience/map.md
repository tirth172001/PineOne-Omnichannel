wayfinder:map

## Destination

A working, prototyped new-user onboarding experience for Pine One Omnichannel: email/password entry → OTP verification → fork between "create new business" and "request access to an existing merchant" (landing in a pending-approval state). Each undecided screen is built/prototyped in this repo as its ticket resolves.

## Notes

- Domain: Pine One Omnichannel (Pine Labs) merchant onboarding, **Singapore market** (Singpass digital ID, ACRA corporate registry, NRIC identity documents, MCC-style business categories). Existing (pre-effort) flow behavior is documented in `docs/flows/onboarding-and-auth.md`; existing components live in `components/onboarding/` (`account-onboarding-flow.tsx`, `lending-application-flow.tsx`, `pos-onboarding-flow.tsx`) and auth in `app/login/page.tsx`.
- Required data/documents per step (PAN, GST, bank details, etc.) are already decided outside this map — do not re-litigate what information is collected, only how the experience collects it.
- Prototype tickets: use the `/prototype` skill. The sequencing ticket: use `/flow-architecture`. Consult `/domain-modeling` if new onboarding vocabulary (e.g. "access request", "authorized signatory") needs pinning down.
- This is a Next.js/Tailwind demo repo with an established design system (see `app/component-docs/`) and its own decision-log convention (`docs/decisions/decision-log.md`). New UX decisions from this map should also be reflected there per the repo's working rules, once implemented.
- Reused as-is (already matches intended experience, no ticket needed): email entry, password creation, OTP verification, the new-business-vs-existing-merchant fork screen, business name capture.

### Standing interaction pattern (post-business-name sequence)

Decided in "Architect the post-business-name sequence" — every prototype ticket in that sequence (tickets 02–10) inherits this unless it says otherwise. **Shell superseded by [Revise progress shell and sub-step transitions](issues/12-revise-progress-shell-and-transitions.md)** — see its Answer for the current shell (no rail; continuous top progress bar; panels match `app/login/page.tsx`'s gap-2/dual-rounded-panel/logo-in-panel convention).

- ~~**Shell**: a persistent, slim left navigation rail (4 macro-sections — Business verification, Business details, KYC, Review and sign — each with sub-steps, jumpable once completed) alongside a main content area.~~ Superseded — no rail.
- **Main content area** is a 50/50 split: **inputs on the left, a live, field-specific preview on the right** (mirrors the login screen's split, reversed). **Revised by [Architect the persistent cross-step preview panel](issues/15-architect-persistent-preview-panel.md):** the preview is now a single component mounted once by the shell (not remounted per step) — its content crossfades between modes (document/banking/owners/signatory) as the user progresses, but it's never a swapped component. See its Answer for the mode list and the running "N details confirmed" header.
- Once a step's core fields are complete, the right panel plays a **shimmer/gleam animation** to signal "verifying" (the "expand to center stage" layout growth mentioned in the original decision was never actually built in any ticket 02–15 implementation — only the internal shimmer sweep was; noted as a pre-existing gap, not fixed by this map).
- **Cards over dropdowns** for small enumerable choice sets (verification method, owners, signatory). Dropdown/searchable-select only where the set is large (business category).
- **Contextual side panels/modals** for "add" sub-forms (add owner, add signatory), not full-page navigation.
- **Success toasts** for confirmations instead of silent state changes.
- **Exceptions to the 50/50 split**: Face authentication (full-width camera capture) and Review/Sign (full-width summary) — both are last-mile screens with nothing left to "preview build."

## Decisions so far

- [Architect the post-business-name sequence](issues/01-architect-post-business-name-sequence.md) — 10-step sequence across 4 macro-sections (verification → basics → store → website/app → banking → owners → signatory → face auth → review → sign); shell was decided as a persistent left rail + 50/50 input/preview split with shimmer-verification, card-selects, side panels, and toasts (see Notes); face auth and review/sign are full-width exceptions. **Superseded:** the left rail was never built and was formally dropped by [Revise progress shell and sub-step transitions](issues/12-revise-progress-shell-and-transitions.md) — no rail, top continuous progress bar only.
- [Prototype: Business verification](issues/02-prototype-business-verification.md) — built 3 variants, picked "Document builds live" (full document preview, skeleton → shimmer → verified). Folded into `app/onboarding/business-verification/`.
- [Prototype: Business basics](issues/03-prototype-business-basics.md) — picked "Document continues building": category + shipping address fill live into the same running Business Profile document from ticket 02. Folded into `app/onboarding/business-basics/`.
- [Prototype: Store verification](issues/04-prototype-store-verification.md) — picked "Document continues building": live map-link row + real uploaded-photo preview, escape checkbox for no storefront yet. Folded into `app/onboarding/store-verification/`.
- [Prototype: Website/app details](issues/05-prototype-website-app-details.md) — picked "Document + browser row": running document plus a live browser-chrome URL bar and app badge. Folded into `app/onboarding/website-app-details/`; closes the "Business verification" macro-section.
- [Prototype: Banking details](issues/06-prototype-banking-details.md) — picked "Document + shimmer extraction": single upload dropzone, shimmer "reading statement…", extracted fields settle into the document. Folded into `app/onboarding/banking-details/`.
- [Prototype: Business owners](issues/07-prototype-business-owners.md) — picked "Row list + donut chart": owner rows with initials avatars, preview is a conic-gradient donut building per owner. Folded into `app/onboarding/business-owners/`. **Superseded:** `_owner.ts` deleted and the donut replaced by the unified `PersonCard` list — see [Unify Owner/Signatory into one Person model + card](issues/14-unify-person-model-and-card.md) and [Architect the persistent cross-step preview panel](issues/15-architect-persistent-preview-panel.md).
- [Prototype: Authorised signatory](issues/08-prototype-authorised-signatory.md) — picked "Role-forward list + letter": stacked cards leading with designation, preview is a Letter of Authorisation filling live with a "Signed" stamp. Folded into `app/onboarding/authorised-signatory/`. **Superseded:** `_signatory.ts` deleted, candidates now come from the real shared owners list — see ticket 14.
- [Prototype: Face authentication](issues/09-prototype-face-authentication.md) — picked "Prep cards + capture screen": identity confirm + 3 prep-tip cards, then a capture screen with an auto-advancing step tracker. Simulated camera (no real `getUserMedia`). Folded into `app/onboarding/face-authentication/`; closes the "KYC" macro-section.
- [Prototype: Review and sign](issues/10-prototype-review-and-sign.md) — picked "Assembled document + inline sign": the running Business Profile document from tickets 02–09 shown whole, with signing appended to the same scroll. Folded into `app/onboarding/review-and-sign/`.
- [Design: Request access to existing merchant](issues/11-design-request-access-existing-merchant.md) — target merchant identified by email/phone lookup with confirm-back-the-business-name step; picked "Conversational framing" (guided back-and-forth, not a form). Folded into `app/onboarding/request-access-existing-merchant/`, its own centered `_shell.tsx` (sibling to the ticket 02–10 rail sequence, not part of it).
- [Revise progress shell and sub-step transitions](issues/12-revise-progress-shell-and-transitions.md) — no left rail (rejected via live feedback, superseding ticket 01's original rail decision); continuous unsegmented progress bar in the same slot the old segmented one had, advancing its "Step X of 4" label only at macro boundaries; fade-up/fade-in-from-bottom sub-step transitions; panels rebuilt to match `app/login/page.tsx` exactly (gap-2, dual rounded-md panels, logo inside the left panel). Folded into `onboarding-rail-shell.tsx`, `step-progress-bar.tsx`, new `onboarding-panel-logo.tsx` and `onboarding-sequence.ts` — all 9 routes in the sequence inherit it.
- [Simplify verification-method selection](issues/13-simplify-verification-method-selection.md) — each `MethodCard` is now its own direct CTA (no radiogroup, no separate continue button); Singpass starts instantly, upload triggers a real file picker; a brief loading beat plays in-place on the clicked card (spinner + status text) rather than as a separate step. Folded into `app/onboarding/business-verification/_variant-a.tsx` only.
- [Unify Owner/Signatory into one Person model + card](issues/14-unify-person-model-and-card.md) — single `Person` type (name, designation, %, isSignatory, verificationStatus) replacing the old disconnected `Owner`/`Signatory` types; unified `PersonCard` (avatar, Signatory badge, verifying→verified animated badge); owners entered in business-owners now really do appear as signatory candidates (shared module-scoped store, survives SPA navigation, resets on hard reload). New: `onboarding-person.ts`, `onboarding-person-card.tsx`.
- [Architect the persistent cross-step preview panel](issues/15-architect-persistent-preview-panel.md) — the preview is hoisted out of each step into `onboarding-rail-shell.tsx` as a sibling of the animated content slot, so it's a genuinely persistent single component (never remounts across the 7 split-screen routes), not a swapped one. One constant frame crossfades between 4 modes (document/banking/owners/signatory) driven by the route; header shows a running "N details confirmed" count across the whole accumulated profile. New: `onboarding-profile.ts`, `onboarding-preview.tsx`.
- [Design post-submission completion/activation](issues/16-design-post-submission-completion.md) — the review-and-sign success screen now explains the activation delay inline and has a real "Go to dashboard" CTA (verified navigating to the actual root route). Deliberately did not build new dashboard-side "activation pending" banner infrastructure (investigated: `AppAlertStrip` is unwired/hardcoded, would be new scope) — flagged as a natural follow-up, not part of this resolution.
- [Add owner validation](issues/17-add-owner-validation.md) — duplicate names and over-100% ownership are both hard-blocked inline in `AddOwnerSheet`, at the field the user is editing, with exact-overflow messaging and a proactive "N% remaining" hint. Verified end-to-end: duplicate name blocked, 120% overflow blocked with correct message, valid 30% addition succeeded and reflected live in the persistent preview.
- [Design the verification-failure pattern](issues/18-design-verification-failure-pattern.md) — business-verification and banking-details both deterministically fail their first attempt (prototype-only trigger; a real integration would key off the actual API/extraction result) and succeed after — same input-side pattern (specific error copy, "Try again," switch-method option where one exists, a no-limit "Contact support" escape hatch) and the same preview treatment (shimmer replaced by a destructive "Verification failed" header badge, mode-specific error content). This closes the map — every ticket (01–18) is resolved.
- **Selector-audit fog resolved without a ticket:** re-examined store-verification, website-app-details, and banking-details (the screens the "General audit" fog item named) — none actually has the selector-then-separate-continue-CTA pattern [Simplify verification-method selection](issues/13-simplify-verification-method-selection.md) fixed on business-verification. All three are already direct forms (checkboxes revealing fields, a single upload dropzone) with no redundant confirm step. No ticket needed; removed from fog.

## Not yet specified

- Broader error/edge-case coverage beyond what's now ticketed (18 covers business-verification + banking-details failure; 17 covers owner-list validation) — e.g. face-authentication liveness failure, storefront-photo upload rejection (wrong file type/size), what happens if a Singpass-verified UEN doesn't match any ACRA record. Will surface as concrete cases once someone builds against this flow for real; not sharp enough to ticket individually yet. ## Out of scope

- Merchant-side approval experience (the existing merchant's view of an incoming access request, and their approve/reject UI) — a genuinely separate surface (likely inside the existing merchant's dashboard) with its own destination; chart separately later.
- Login screen redesign — login is treated as functionally fine; only correct auth-state routing to/from it is required (see Notes), not a new experience.
